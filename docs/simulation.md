# Simulation Systems Plan

## Purpose

This document defines the authoritative simulation model and the gameplay-system invariants that all vertical slices must preserve.

## Simulation Principles

- The server owns time, state, validation, and outcomes.
- Client messages express intent, not authoritative results.
- Zone-local state uses a single in-process writer wherever practical.
- Mutations are durable before they are replicated as successful.
- Every gameplay system supports restart and replay testing.
- Tunable gameplay data is externalized from core execution logic.
- Derived presentation data is rebuildable from canonical state.

## Core Gameplay Loops

1. Gather
- Dig, forage, mine, fell trees, harvest, fish, and farm.

2. Process
- Saw, smelt, grind, cook, refine, and assemble intermediate materials.

3. Craft and Build
- Craft tools, improve quality, plan structures, deliver components, and complete parts.

4. Maintain
- Repair, reinforce, preserve, feed, refuel, and pay upkeep.

5. Trade and Organize
- Exchange goods, specialize production, establish permissions, and form settlements.

The first implementation proves only terrain mutation, then one physical tree workflow, then one construction part. Breadth follows correctness.

## World Clock and Scheduling

- The world server owns a monotonic simulation clock.
- Zone executors process queued commands at a configurable authoritative cadence.
- Timed actions use authoritative deadlines and persisted state, not client timers.
- Low-frequency systems such as decay or ecology run on scheduled intervals or elapsed-time catch-up.
- Dormant zones may reduce simulation frequency while retaining deterministic catch-up rules.

Wall-clock timestamps are recorded for audit and operations, but gameplay ordering depends on authoritative sequence, revision, and simulation-time fields.

## Unified Action Pipeline

Every mutating gameplay action follows:

1. `Validate`
- Session, actor, protocol, command shape, range, permissions, tools, revisions, and domain rules.

2. `Reserve`
- Reserve required zone, chunk, entity, or container resources.
- Prevent conflicting actions from consuming the same resource.

3. `Execute`
- Track authoritative deadline, ticks, or work accumulation.
- Observe interruption conditions.

4. `Resolve`
- Calculate skill, quality, damage, output, and state-transition results.
- Produce a deterministic normalized commit plan.

5. `Commit`
- Commit domain state, audit history, command result, stream sequences, and outbox records atomically.

6. `Replicate`
- Publish committed snapshots or deltas.
- Client progress and completion UI follows server events.

No action completion is accepted from a client.

## Randomness

Where actions require randomness:

- Random outcomes are generated by the server.
- The random source and seed strategy are testable.
- Final resolved outcomes are persisted as part of the action result.
- Recovery never rerolls an already committed action.
- Security-sensitive or economy-sensitive randomness must not be client-predictable.

Deterministic replay means replaying committed outcomes and state transitions, not necessarily recreating every random draw from a global seed.

## Skill and Quality Model

Initial direction:

- Skill values use an explicitly bounded numerical representation.
- Item quality influences durability, effectiveness, and outputs.
- Difficulty calculations are data-driven.
- Failure results are typed and may include no output, reduced output, damaged input, or lower quality.

Exact progression curves are deferred until the action pipeline and first physical workflows are functional.

## Terrain and Terraforming

### Source of Truth

- Surface terrain uses world-space corner heights in integer decimeters.
- Tile slope, normals, collision, and mesh data are derived.
- Tile material and flags are separate canonical metadata.
- Underground terrain is deferred.

### Partitioning

- Terrain uses fixed chunks grouped into zones.
- Every world corner has one canonical owner chunk.
- Neighbor chunks may expose rebuildable borrowed-border values.
- A border mutation updates canonical owners atomically; it does not create two writable copies of one corner.

### Initial Mutations

- Dig: lower one legal corner by a bounded amount.
- Drop: raise one legal corner by a bounded amount.
- Level and flatten: later server-generated patterns composed of legal primitive deltas.

### Terrain Invariants

- One canonical owner per world corner.
- No mutation without zone authority and idempotency handling.
- No partial multi-owner commit.
- Expected revisions are validated before mutation.
- Derived terrain data can be rebuilt exactly from canonical state.
- Snapshot plus mutation-tail replay equals uninterrupted state.

## Entities and State Machines

Persistent world objects use explicit state machines and monotonic revisions.

Examples:

- Tree: standing -> felled -> processed -> stump -> removed.
- Build part: planned -> framed -> partial -> complete -> damaged -> ruined.
- Action: scheduled -> active -> interrupted, cancelled, failed, or committed.

Requirements:

- State transitions are validated server-side.
- Invalid transitions are rejected without side effects.
- Every committed transition is auditable.
- Repeated commands return stored outcomes rather than repeating transitions.

## Inventory and Containers

- Every item instance has one canonical owner location.
- Container graphs may not contain cycles.
- Moves, crafting consumption, and construction delivery commit transactionally.
- Quantity and quality conservation rules are covered by property or integration tests.
- No gameplay system mutates inventory outside the shared command and transaction path.

## Ecology and Creatures

Deferred until the core vertical slices are stable.

Future direction:

- Creature needs, aggression, habitat, and carrying capacity.
- Spawn and migration pressure by biome and player activity.
- Lower simulation frequency for distant populations.
- Persisted aggregate state where per-creature simulation is unnecessary.

## Decay and Upkeep

Deferred until construction is persistent.

Future direction:

- Material, quality, exposure, and maintenance influence decay.
- Decay is calculated from authoritative elapsed time.
- Catch-up has bounded work and cannot duplicate damage.
- Settlement upkeep transitions are explicit and auditable.

## Permissions

Permission checks are server-side hooks in validation and commit planning.

Initial terrain and construction slices may use simple ownership fixtures, but the interface must support later:

- Deeds and settlements.
- Role-based permissions.
- Public, allied, and individual access.
- Temporary reservations and contracts.

## Protected Invariants

- No item exists in multiple canonical locations.
- No committed resource is consumed twice.
- No action completes without authoritative execution and commit.
- No terrain corner has multiple writable owners.
- No multi-owner terrain mutation partially commits.
- No state transition rerolls or replays after durable success.
- No client sequence gap is silently ignored.
- No recovery path invents state absent from canonical persistence.

## Required Testing by System

Every simulation feature includes:

- Unit tests for pure rules.
- State-machine transition tests.
- Integration tests against PostgreSQL when persistence is involved.
- Duplicate-command and concurrency tests.
- Disconnect and restart tests.
- Failure injection around every durable boundary.
- Metrics for rejection, latency, contention, and recovery failure.

Gameplay breadth does not override these gates.
